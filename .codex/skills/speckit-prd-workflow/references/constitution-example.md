# Constitution Principle Example

Use this as a calibration example for the right abstraction level. It is not a template to copy verbatim.

## Example

### 1. Preserve User Context

Features must keep user context visible at decision points. Product flows should not force users to act on recommendations or outputs without enough surrounding information to judge relevance.

Why this belongs in the constitution:

- It is a durable product promise.
- It can shape multiple future features.
- It is broader than any one screen or workflow.

### 2. Keep MVP Scope Narrow

Specifications must prefer the smallest coherent workflow that solves the core user problem. Future-scope ideas should be recorded separately instead of blended into current-scope requirements.

Why this belongs in the constitution:

- It is a reusable scope-control rule.
- It affects many future spec decisions.
- It prevents feature creep during PRD-to-spec translation.

### 3. Require Testable Product Outcomes

Every spec must include measurable or falsifiable success criteria tied to product outcomes rather than generic engineering completion.

Why this belongs in the constitution:

- It governs how every future spec is written.
- It keeps work aligned to outcomes instead of output volume.

## Anti-Examples

These do not belong in the constitution:

- "Add a weekly digest email."
- "Use PostgreSQL for event storage."
- "The settings page should show a tabbed layout."

These are feature, implementation, or UI decisions rather than durable product principles.
